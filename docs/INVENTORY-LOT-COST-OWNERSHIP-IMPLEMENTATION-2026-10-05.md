# Inventory lot and cost ownership: approved Batch B

The approved change separates physical stock authority from accounting readiness. Missing historical cost evidence no longer vetoes independently valid physical work: the existing transaction posts that work together with an immutable accounting obligation. A cost-only revision no longer invalidates an unchanged claim's lot identity. Neither statement certifies the accuracy of historical prices.

The user's F11 decision was explicit: “yes, all of the cost data is completely wrong anyway.” This approves the missing-evidence admission policy discussed in the [historical revalidation](INVENTORY-LOTS-COST-CURRENT-STATUS-2026-10-05.md). It does not authorize history repricing, invented receipts, known zero prices, incident recovery, production activation, merge or deployment. The October 1 report and protected primary/recovery work remain unchanged.

### Physical work and cost-only recovery

1. [recordLotCostContribution](../server/modules/inventory/infrastructure/cost-evidence.repository.ts#L88) validates exact source/output quantities and graph intervals. A null/zero historical receipt basis produces `COST_HISTORICAL_BASIS_MISSING`; an insufficient positive basis, cycle or conflicting output still rejects. No original intake quantity is invented.
2. [recordLotCostFollowUp](../server/modules/inventory/infrastructure/lot-cost-follow-up.repository.ts#L22) writes immutable evidence, actor/time and a stable operation/lot identity with a fingerprint. Failure to persist it rolls back the stock operation. [pickResources](../server/modules/inventory/infrastructure/canonical-claim-inventory.repository.ts#L1383) records uncertain picked costs inside the same transaction, after quantity admission. Existing quantity replay is checked before a changed lot can create a different obligation.
3. Canonical transformation execution [binds locked lot costs](../server/modules/inventory/infrastructure/canonical-claim-inventory.repository.ts#L1916) into copied pricing inputs. Price snapshots no longer substitute for physical identity. Graph locking serializes these reads against financial revision; recorded physical claims and package/build authorization remain intact.
4. [applyCostRevision](../server/modules/inventory/application/apply-cost-revision.ts#L29) remains the financial application owner. It uses actual receipt origins and contribution edges, respects manual protections, keeps missing basis/residual/unsupported credit outcomes in durable review, and records follow-up attempts in its financial transaction. It changes costs/COGS, not quantities. There is no new ATP or financial engine.
5. [COGSService.cascadeRecostForLotMills](../server/modules/inventory/cogs.service.ts#L135) applies exact signed extended amounts to both positive picks and negative unpicks. Reversal rounding uses the same magnitude as positive rounding. Linked pick/unpick rows remain compatible with a later partial return.

The post-commit proof uses committed database evidence and replay through the existing owner: physical work is not repeated when costing is resumed; a repeated financial application reads its durable result; concurrent applications serialize; injected obligation, financial-attempt and final return-receipt failures roll back their entire owning transaction. These tests do not prove that a production worker is enabled or that arbitrary missing historical lineage can be reconstructed automatically.

### Returns and picker impact

[applyReturnedStock](../server/modules/inventory/application/return-restock.use-case.ts#L98) creates one lot per exact returned cost layer, retaining source COGS allocation, component mills, confidence, units and audit identity. [allocateReturnCosts](../server/modules/inventory/infrastructure/return-cost-allocation.repository.ts#L28) never selects a latest same-SKU row from a different order/item. A return does not consume its original source lot again.

[ReturnsService.processReturn](../server/modules/orders/returns.service.ts#L103) keeps the portal-owned purchased-line fence, locks source order/items and independently bounds physical returns by ordered variant quantity less nonvoided recorded returns. This protects unknown-cost returns too. Its stable supplied command key serializes and replays the whole batch before mutable location or quantity checks. Older callers may omit the key for compatibility; those callers do **not** gain safe request replay.

[quarantineReturnedStock](../server/modules/inventory/application/quarantine-returned-stock.ts#L10) removes only the newly returned damaged/defective layers in that same transaction, protecting reserved, picked and packed custody. Active stock projections still belong to the quantity journal; the separate existing consumed counter remains cost-lineage metadata. Return history retains the damaged/defective condition across all returned layers.

The [shared HTTP contract](../shared/inventory/return-command.ts#L5) validates input and exact result identity/quantity/condition and summary consistency. [The registered handler](../server/modules/inventory/inventory.routes.ts#L910) rejects malformed bodies before work and suppresses private unexpected-error details. [The existing persisted command requester](../client/src/lib/inventory-command.ts#L36) retains intent until a valid acknowledgement; [Returns receiving](../client/src/pages/Returns.tsx#L145) can check the original result after reload even when the full return has already exhausted returnable stock. It never generates a replacement key for that check.

The picker gets no accounting decision or separate physical replenishment workflow. Existing rules/resolvers still own inline replenishment. Stock shortage, another claim's custody, wrong SKU/bin/units, missing package/build authority, freeze, invalid money or conflicting evidence remain real errors. The pre-existing best-effort post-return replenishment callback is not converted into a general durable scheduler by this batch.

### Exact valuation and compatibility

[normalizeLotCosts](../server/modules/inventory/domain/lot-cost.ts#L56) preserves supported legacy values, rejects negatives/fractions/unsafe numbers/overflow, and requires authoritative components to reconcile. [lotCostNeedsReview](../server/modules/inventory/domain/lot-cost.ts#L113) is the same confidence policy for operational outputs and valuation. Legacy residual component estimates are explicitly provisional; they are not newly confirmed purchase facts.

[readInventoryValuation](../server/modules/inventory/application/read-inventory-valuation.ts#L9) reads the same active on-hand lots for both report shapes and obtains Catalog display identity through its [published reader](../server/modules/catalog/inventory-cost-display.reader.ts#L13). [valueInventory](../server/modules/inventory/domain/inventory-valuation.ts#L13) keeps exact bigint arithmetic, a stable variant tie-break and one reporting-rounding boundary. Existing numeric fields are retained with additive exact-mills strings, `quantityUnit: "variant"` and unknown-cost quantities. The legacy product key `avgCostPerPiece` denotes an average per recorded lot variant unit; mixed package quantities are not silently converted to physical pieces.

Unknown cost remains null in immutable financial source evidence. Existing numeric non-null compatibility columns use a provisional/unresolved representation, which the shared policy never certifies as a known zero. No historical rows are repriced or backfilled by the new migrations.

## Remaining work, assumptions and failure modes

The policy assumes physically eligible work has independently valid authority; accounting uncertainty is not permission to fabricate work or repair conflicting custody. Exact numeric validation and recorded confidence do not establish that a historical source price was correct.

Historical lots without trustworthy origins/basis require reviewed evidence and a separate remediation plan. The follow-up endpoint exposes durable obligations and application outcomes; this batch does not add a general worker to synthesize missing history, clear uncertainty automatically or activate the existing receipt worker. Component-only revision may leave a lot provisional until its other evidence is established.

Broader Batch C ownership/cleanup, legacy non-OMS source/fulfillment mapping, older no-key request retry, two-step legacy manual-cost CSV/import paths, and compatibility-table/external consumers remain outside closure. Do not delete `inventory.order_line_costs` history merely because the searched runtime no longer owns operational costing there.

Material failure modes are incomplete accounting evidence remaining in review; invalid/conflicting data still blocking work; failed obligation/audit persistence rolling back the whole transaction; missing client retry storage requiring verification; no-key legacy retries lacking replay safety; unsupported uniform-cost residuals requiring review; and source/graph size or numeric limits producing explicit errors instead of partial success. These are limits to expose, not reasons to invent a receipt, a price or another physical posting.
