## Operator behavior after deployment

1. **Sync an existing listing.** The server saves the request, verifies the actual eBay identities and updates through the existing quantity owner. One rejected product does not discard other products' results. The row distinguishes a listed product from an update that is queued, recovering, blocked or verified complete.
2. **A temporary read/network/storage failure.** Saved maintenance work retries within its bounded policy. Once manual attention is needed, the issue offers the appropriate retry/status action. eBay cooldowns remain enforced; repeated clicks do not shorten them.
3. **An old unknown quantity request.** “Review blocked update” displays the exact attempt and recorded response. An operator with `channels:edit` and `inventory_planning:activate` reviews and explicitly authorizes “Resume with current inventory.” The original outcome stays unknown in the audit history; fresh work uses current canonical inventory. An active request or a request covering additional listings cannot be bypassed by this dialog.
4. **A mapping problem.** The dialog shows catalog SKU, eBay SKU, offer, listing and observed group when available. A legitimate catalog rename is supported. Conflicting or incomplete membership remains blocked until the mapping is corrected and verified.
5. **A connection/configuration problem.** The message points to connection settings or the relevant product settings. Unrecognized failures remain visible with copyable diagnostics rather than being silently retried or presented as success.

This work does not automatically recover historical attempt 16323 or resync every listing. Those are production operations and require the deployed code plus an authorized operator action. Existing shared/variant photo assignment remains with the canonical catalog photo resolver.

## Transactions, idempotency and migration impact

- `0732_ebay_listing_sync_identity_admission.sql`: separate immutable admission-failure journal and immutable observed provider identity on saved jobs, with owned stage evidence required for binding. Existing source identity is retained.
- `0733_ebay_provider_response_finality.sql`: nullable request finality evidence. Historical rows remain null; installation does not resolve old requests.
- `0734_ebay_operator_republication_recovery.sql`: immutable recovery commands and preserved attempt snapshots; database guards require exact locks, one transaction, all affected scopes and complete audit members. No quantity is chosen by the migration or recovery repository.
- Publish and maintenance share a product workflow lock. Initial publication also limits simultaneous workflows before pool checkout, reserving capacity for inventory admission/evidence work. Shared quantity resource locks remain the authority across actual provider requests.
- Replays, concurrent workers/operators, changed preview/source identity, local rollback and restart after a committed provider response are tested separately. A provider response and a local commit are separate facts.
- Recovery command keys are globally unique. Two concurrent recoveries on disjoint listing scopes using the same key produce one committed decision and a typed replay conflict; the losing transaction retains its original attempt and writes no catch-up or audit member.

## Limits, risks and unproven behavior

- **No deployment proof:** local passes do not establish GitHub CI, migration installation, Heroku release health or live eBay behavior. Those must be checked on the final PR/release separately.
- **Unknown historical responses:** incomplete evidence is not converted into a success or fabricated rejection. Operator recovery explicitly authorizes new work while preserving uncertainty. Requests covering additional listings still need a review of their complete scope.
- **Initial publication is synchronous:** interruption stops a batch between products; an in-flight product finishes its local projection when the process survives. A server crash requires retry/discovery. This PR does not invent a second durable publication engine.
- **Interrupted destructive rebuild without its original review:** a withdrawn group cannot be rediscovered by a published-only observer. The server refuses a catalog-derived group guess and directs an administrator to recover the original group/offer mapping. Fully durable rebuild intent is a remaining lifecycle improvement.
- **First publication with lost mapping plus a changed remote group:** the product recovery preview can lack sufficient original group identity and report a broader scope. Automatic expansion would be unsafe; no historical group is guessed.
- **Provider read throttling:** the existing registration read transport does not expose Retry-After headers to the observer. Identity read failures use bounded retry classification; mutation transport retains actual provider cooldown evidence.
- **OAuth across processes:** refresh coalescing is local to one service instance, while conditional database updates protect reconnects across instances. The session challenge tests prove sequential consumption; they do not prove atomic simultaneous callback consumption across multiple dynos. Provider authorization-code single use remains required.
- **Ancillary settings and feed architecture:** older taxonomy/policy settings still have conventional toasts, and the feed/reconcile routes retain legacy read/orchestration responsibilities. They are not presented as a complete architectural rewrite. The new persistent issue/recovery contract covers listing operations and connection health.
- **External effects:** a successful eBay mutation cannot be rolled back by rolling back PostgreSQL. Identity fencing, retained response evidence, readback and explicit recovery address this boundary; they do not create a distributed transaction.

No assumption that a matching current quantity proves historical delivery is used. No replacement ATP formula, invented stock, zero cost, order recovery, cutover or automatic production activation is included.
