### F11A: a cost denominator is a physical veto

1. `ReplenishmentUseCases.executeTask` resolves the frozen task, pins server transformation authority, locks the task and invokes the transaction-bound `InventoryUseCases.executeReplenishmentMove`. Movement, completion and the durable follow-up are inside its transaction. Completed replay recovers the follow-up before returning. [Task transaction/replay:1428–1569][task]
2. Direct case-SKU replenishment uses `InventoryUseCases.transfer`; that method opens a transaction, validates units/locations and protects reservations before calling the lot owner. `InventoryLotService.transferLots` selects unreserved FIFO layers, decrements their physical quantities, creates matching destination layers, and calls `recordLotCostContribution` for each source/output pair. [Direct route:1736–1748][replen-direct] [Transfer admission:1933–1985][transfer] [FIFO movement and evidence:1042–1199][transfer-lots]
3. Replenishment case conversion likewise consumes exact source lots, allocates exact output cost layers, and calls `recordLotCostContribution` before the quantity operation finishes. It already propagates `consumedCostProvisional`; this specific output path is not the F15 confidence defect. [Conversion:1756–1918][replen-conversion]
4. `recordLotCostContribution` reads `source.qty_received` and `output.qty_received`, and calls `costInteger(..., minimum=1)`. A zero source denominator throws `COST_EVIDENCE_INVALID_INTEGER`; an insufficient positive denominator rejects the interval. Neither result is a test of source on-hand ownership. The surrounding transaction therefore cannot complete that movement. [Guard:106–145][contribution] [Integer validation:22–27][cost-integer]

The controlled audit proves the repository rejection with `source_qty=0`, output quantity 1 and contribution quantity 1. The full current-code transaction proves where that rejection propagates; **this pass did not run a real PostgreSQL movement/rollback counterexample**. A bin with four otherwise valid physical units and missing historical receipt metadata is a conditional example, not a claim about a particular live bin.

Do not remove the accounting interval guard or fabricate a receipt/denominator. The proposed correction is an explicit missing-evidence outcome and durable cost obligation attached to the existing physical operation receipt.

### F11B: a price snapshot is part of physical ownership

`reserveResource` freezes component mills into each lot allocation. `pickResources` locks exact levels/lots, then `validatePickInventory` compares live cost components to that allocation and throws `CLAIM_PICK_LOT_COST_CHANGED` before posting any physical pick. Transform execution throws `CLAIM_LOT_COST_CHANGED`; observed relocation throws `CLAIM_OBSERVATION_SOURCE_COST_CHANGED`. [Claim snapshot:618–635][claim-snapshot] [Pick:1388–1450,2575–2623][claim-pick] [Transform:1921–1939][claim-transform] [Observation:1070–1087][observation-cost]

The legitimate cost-application path is `reconcilePurchaseCostEvidence` → `applyCostRevision` → `COGSService.revalueComponent` → `revalueLotCostMills`. It locks and revalues lots, cascades into `oms.order_item_costs`, and records cost applications, before/after evidence and reporting events. These functions do not refresh the frozen claim allocation cost. [Application:84–92][purchase-cost] [Cost graph/application:28–193][apply-cost] [Revalue and COGS cascade:115–198,289–306][recost]

`PickingUseCases` retries a short claim or recorded/observed location shortfall. Its eligible codes do not include these cost-change errors. The canonical pick transaction rolls back and retries serialization failures; it does not reconcile a valid cost-only change. [Picker recovery:1691–1757][picker-recovery] [Serializable/replay:5530–5561; rollback:5827–5863][pick-transaction]

The audit changed only live cost from 100 to 120 mills: exact lot, variant, bin, claim resource, four on-hand units and one reserved unit stayed consistent. A one-unit pick still rejected, with no writes. This proves the cost-snapshot veto with mocked database boundaries; it does not prove its live frequency or real concurrent locking behavior.

### F12: restock loses the original economic identity

The registered admin inventory-treatment route validates input/actor and calls `ReturnCaseOperationService.applyInventoryTreatment`. The service serializes command replay and disposition state through `PostgresReturnCaseOperationStore.transaction`; `persistInventoryTreatment` supplies distinct OMS, WMS and WMS-item IDs to `applyReturnRestock`. [HTTP:293–318][return-http] [Application:504–580][return-app] [Store:137–139; caller:711–769][return-store]

Despite receiving all three identities, `applyReturnRestock:138` calls `resolveReturnCost` with **`input.omsOrderId`**. `resolveReturnCost` searches `oms.order_item_costs.order_id`, whose FK references WMS `orders.id`, imported from `orders.schema.ts`. It filters only order and SKU variant, sorts by descending cost-row ID and takes one row. It does not select the returned WMS item, exact FIFO allocations or returned quantities. [Restock:138–203][return-restock] [Query:99–119][return-resolver] [FK/import:16,385–398][cogs-schema]

The resolver reads only `unit_cost_cents`; restock multiplies it by 100, assigns the entire amount to the product component, writes packaging/landed zero, and creates one returned lot. It does not record a cost origin or contribution. A zero COGS row falls through to another provisional source. Existing cost applications discover descendants through contribution edges, so this return does not establish that source relationship. This is not proof that every possible manual repair or unrelated future financial path is unavailable. [Restock writer][return-restock] [Graph traversal:35–71][apply-cost]

The audit used distinct OMS=51, WMS=61 and WMS-item=71. It captured cost-query parameters `[51,301]`, and an input row containing 149 mills plus a rounded 1-cent mirror became 100 mills on the returned lot. No cost edge was written. Mocked rows demonstrate the selected identity/precision; they do not establish that a wrong live order happened to share the queried ID.

**Compatibility reach:** `client/src/pages/Returns.tsx.processReturnMutation` still posts `/api/returns/process`; `inventory.routes.ts` calls the composed legacy `ReturnsService.processReturn`, which invokes the same resolver. That path validates the source order/item and blocks portal-owned purchased lines in favor of canonical receiving. It is **not dead**. Fix the shared cost-allocation policy for its supported scope without bypassing the portal/return-case fence or introducing a second calculator. [UI:143–158][legacy-return-ui] [HTTP:908–924][legacy-return-http] [Source fence:99–148; cost calls:178,224][legacy-return]

### F13: fallback occurs before invalid evidence is rejected

`preferredMills` returns mills only when they are positive. `normalizeBuildLotCosts` also selects total versus unit columns by positivity, then checks the normalized results for negatives. Thus a negative authoritative mill value can be hidden by a positive cent mirror; an explicit zero cannot be distinguished from a default/unpopulated zero through this function. [Selection:123–145; normalization:244–297][money]

The audit returns 10,000 mills for a fixture with total/unit/product mills = -500 and corresponding cents = 100. A zero-mill fixture with 7-cent mirrors becomes 700 mills. The latter proves missing authority classification, **not that all current zero columns are known-zero evidence**: legacy mill defaults need a proven provenance/compatibility contract.

Reuse the existing `costSourceRevisionSchema`, which already distinguishes estimated, confirmed, unknown and review-required evidence, and permits an explicit known zero. It retains unknown amount/denominator as null and requires an actionable issue. Negative economic credits remain source facts; an unsupported negative lot value must not be made positive by fallback. [Existing contract:3–89][cost-contract]

### F14: reports have two arithmetic owners

`InventoryLotService.getInventoryValuation` sums on-hand quantity times `total_unit_cost_cents`/`unit_cost_cents`, grouped by variant. It feeds `/api/inventory/valuation` and `/api/reports/inventory-valuation`. `COGSService.getInventoryValuation` sums mills grouped by product, rounds each product, then sums those rounded cents for its grand total; it feeds `/api/cogs/valuation`. [Variant owner:1250–1308][valuation-lot] [Product owner:757–817][valuation-cogs] [Routes:1268–1275,2600–2607][valuation-http] [Report:30–37][valuation-report]

For three units at 149 mills each with a 1-cent unit mirror, the variant query extends 3 cents; extending exact mills first gives 447 mills, rounded to 4 cents. Mills here are **1/100 cent**. Additional differences can arise from grouping-rounding boundaries. This arithmetic counterexample and source trace establish different algorithms; this pass did not execute both actual SQL queries on a disposable database.

Preserve response shapes, but make them projections of one exact aggregate/read policy. Declare the unit basis at each variant/product grouping, round at a single defined reporting boundary, and reconcile displayed group totals under a deterministic remainder rule if additivity is required. Do not retain both calculations and merely compare their outputs.

### F15: money is conserved but confidence is not consistently carried

`executeTransformationOperation` selects cost columns without `cost_provisional`, validates claim costs, and inserts canonical build/conversion outputs with a literal confidence marker 0. `BuildExecutionRepository.executeInTransaction` likewise inserts ordinary build outputs with marker 0. Both already record contribution edges. This finding is loss of confidence classification, not an assertion that their exact cost allocation or all lineage is absent. [Canonical source:1871–1877; output:2127–2169][canonical-output] [Ordinary build:1076–1130][build-output]

In contrast, `transferLots` copies source confidence, replenishment conversion carries the consumed marker, and observed relocation validates/copies the source marker. These sound behaviors should become one shared evidence/layer rule, with persistence adapters appropriate to each existing owner. [Transfer:1116,1187][transfer-lots] [Replenishment:1870][replen-conversion] [Observation:1159–1172,1251][observation-confidence]

## Proposed implementation contract

This is a proposal, not implemented behavior.

1. **Separate physical admission from cost readiness.** Preserve exact variant, warehouse, location, lot/claim ownership, quantity units, permissions, freezes and server conversion/build authority. A valid cost-only revision must not require releasing/replanning unchanged physical ownership. Bind the applicable cost evidence under the existing locks and save its version with the operation receipt. Replay uses committed evidence/result; it does not select another price or post another movement.
2. **Handle missing history explicitly, subject to F11 agreement.** If verified physical work is eligible but the accounting denominator/origin is genuinely unavailable, commit the physical operation and a durable, uniquely keyed cost obligation in the same transaction. Reference the existing quantity/command receipt, exact source/output lots, actual taken/produced quantities and frozen units, actor/reason/time, known component mills, evidence versions and missing basis. Preserve known money and estimated/unknown classification. Do not invent a receipt, original intake quantity, zero price, confirmation of work or a valid contribution interval. Invalid/conflicting evidence still rejects or requires explicit review; inability to persist the required obligation rolls back the operation.
3. **Reconcile costs through the existing financial owner.** Establish missing lineage only from authorized evidence; then apply exact component revisions through the existing graph/application/COGS owner. Record an immutable attempt/result and durable follow-up. Recovery after financial commit must resolve the same obligation without a second quantity posting. A review-required result must remain visible and must not be automatically retried as if it were a transient outage. Required work survives process restart and notification failure.
4. **Use one strict cost/evidence primitive.** Extract the pure component/total parsing and layer/confidence decisions from infrastructure, then route all operational callers through it. Reuse existing evidence vocabulary, component protections and exact allocation primitives. Select legacy cent compatibility from proven record provenance/version, not `> 0`, `NULLIF(...,0)` or `||`. Distinguish valid known zero, estimates, missing evidence and invalid data; validate overflow and component reconciliation before any write. Avoid a blanket change that turns historical cent-only stock into free inventory.
5. **Restore exact return lineage.** Use typed OMS/WMS/WMS-item identities and the actual sold/picked lot allocations associated with the returned line/fulfillment. Allocate only the returned quantity across those layers with stable attribution and exact mills/components/confidence. Partial returns, repeated SKUs and multiple lots cannot use “latest same SKU.” Extend the cost lineage contract for an attributable return; do not pretend it is a new purchase receipt or physically consume the original lot again. Both reachable return flows delegate to this owner while retaining their distinct authorization fences.
6. **Use one valuation owner.** Read the same exact cost/evidence model and aggregate integers before rounding. Preserve the three existing HTTP contracts as projections. Define mixed package/SKU unit grouping explicitly and test the same grand valuation under both variant and product views. Remove the replaced calculations and obsolete cost/confidence helpers once their actual callers migrate.

The existing receipt-cost queue is a useful implementation foundation: `enqueueReceiptCostRequests` commits work with stock, while `processReceiptCostRequests` records financial outcomes separately and preserves pending requests on failure. Its recovery repository leases/fences work and recovers a financial commit preceding job completion. **Its present eligibility is limited to real closed receipts with existing requests; it does not cover arbitrary historical movement/claim/return obligations.** Reuse its narrow recovery mechanisms/financial owners where appropriate; do not fake receipts to enter its queue or build a generic second inventory engine. The current worker's environment activation is a separate control and was not checked or changed. [Queue:28–109][receipt-queue] [Eligibility/recovery:47–82,87–138][receipt-recovery] [Worker:19–64][receipt-worker]

## Required approval and picker impact

**The business decision:** must accounting finish repairing missing history before the warehouse can use otherwise valid stock?

Example: the system verifies four cases in reserve and the normal rules authorize moving one case into the pick bin. Its old receiving/cost record is incomplete. Should that valid movement continue while accounting resolves the missing history, or should warehouse work stop until accounting fixes it? This is a conditional example, not a statement about a current bin.

Recommendation: **allow that physical operation and record the cost obligation**, retaining all known costs and exact identity/claim/quantity protections. Do not fabricate a zero cost or denominator. Invalid/conflicting evidence, unavailable stock, another order's reservation, incorrect units/identity, a freeze or missing transformation authorization still blocks. This decision does not authorize a production repair, worker activation or historical bulk admission.

Under the proposed policy, a picker does not get a cost-only “no inventory” rejection for unchanged, owned physical stock. The server owns inline replenishment and costing; the picker has no new accounting decision or separate replenishment workflow. Missing physical stock/authority remains a real exception. Durable accounting work must be visible and recoverable; allowing movement without its required evidence record is not success.

## Assumptions, risks and failure modes

The user's Inline replenishment setting is retained as session context; current production configuration was not inspected. No missing-data frequency, deployed admission outcome or worker activation is assumed. The proposed F11 exception is limited to genuinely unavailable historical accounting evidence with independently valid physical authority; conflicting/invalid data is not automatically classified as merely missing.

Material risks are accidentally converting ambiguous legacy costs to authoritative zero; losing a component or return allocation; carrying a stale price into COGS; resolving a cost obligation without updating all descendants; changing units/group rounding between endpoints; replacing a safe blocking error with an unrecorded success; deadlocks from changed graph/lot lock order; and replaying physical work after response loss or post-commit failure. Each maps to the required exit proof above. The long-lived primary/recovery/other branches create an additional integration risk; they must remain preserved and be compared to fresh main before implementation.
