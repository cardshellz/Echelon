## Concrete transaction and lock order

1. **Handoff / full assembly posting:** existing canonical authority -> graph products -> WMS order and items -> claim -> operation/resources/build/inventory locks -> warehouse/identity/relevant location context -> task fence/evidence -> canonical receipt -> one commit. On completion, the warehouse fence is checked after owning inventory locks; a failure rolls back all writes, including inventory and costs.
2. **Start / block / resume:** preliminary task read without a lock -> WMS order -> WMS item -> canonical claim -> warehouse/identity/relevant locations -> task -> state plus command/event receipt -> one commit. This path never calls a stock writer or acquires graph/inventory locks afterward.
3. **Claim release / replacement / count displacement:** existing canonical lock sequence and claim fence -> warehouse work recovery guard -> existing build-reservation and inventory release paths, all in the caller's transaction. Task start takes that same order/claim fence, so it cannot begin in the middle of claim release.
4. **Queue/detail/authorization reads:** read transaction only. `AssemblyWorkService.handoff` and `complete` finish their preliminary authorization/read transaction before invoking the canonical owner. They never hold warehouse/task locks while starting a second canonical transaction.

Configuration editing uses its existing warehouse-first lock order and does not acquire claim or inventory locks. Started work retains its profile/station snapshot. Pausing a station stops new starts but does not prevent the assigned worker from recording already-started completion, provided current role/scope and the inventory owner's preconditions permit it.

## What is likely / what is not proven

- Confirmed user operating requirement: materials are already at the assembly station, picker prints the label before assembly, and one person may assemble and pack at the same bench.
- No actual station, bin, employee grant, SKU route, active claim, or production authority state was inspected or changed here. Which real location IDs satisfy a job is **not proven**; the backend requires explicit bindings and existing canonical resource evidence instead of choosing them.
- **HYPOTHESIS:** the new work-only primitive will support the two-person handoff without a separate login/station for each activity. That is not an end-to-end usability result until the gun and bench screens are connected and exercised.
- The existing canonical build command posts a **whole planned build** (`server/modules/inventory/infrastructure/canonical-claim-build.repository.ts`, `executeOperation`, including full-run and build-order completion at lines 580–718). This checkpoint does not add partial lot/cost posting. A partial/incomplete physical build must be blocked, not falsely completed; generic cancellation is refused once physical work starts.
- A safe supervisor recovery/reassignment path for started or cancelled physical work is still required. The guard prevents blind inventory release; it is not that recovery workflow.
