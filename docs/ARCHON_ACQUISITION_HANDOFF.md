# Order acquisition evidence forwarding

`pushToMissionControl` now includes `order.marketing_attribution` on ordinary order events. It reads only the explicit canonical array or the dedicated Shopify note attribute `__archon_acquisition_v1` (legacy `archon_acquisition_v1` is accepted). Coupon codes, consent, financial fields, order identities, and inventory behavior remain unchanged.

`archon-acquisition-contract.ts` is a source snapshot of the published extraction/validation contract from cardshellz/archon commit `f819c6a`: `sourceKeySchema` and `touchInputSchema` from `shared/source-attribution.ts`, plus `readStorefrontAcquisition` and `extractStorefrontAcquisition` from `shared/storefront-acquisition.ts`. It uses Echelon's existing Zod dependency. Archon remains the owner of classification, attribution windows, evidence deduplication, and revenue calculation; Echelon only validates and transports captured evidence. Updates to that protocol must synchronize these source blocks and their contract tests.

Malformed evidence produces an `oms.archon_acquisition.forward` error with code `INVALID_MARKETING_ATTRIBUTION`, classification `permanent`, outcome `tracking_requires_review`, and the OMS order ID. Logs exclude customer attributes, URLs and credentials. The financial order still goes out with an empty evidence array. This is a log diagnostic, not a new retry/dead-letter subsystem. Existing order delivery behavior is unchanged; tracking failures do not stop checkout or order delivery.

Deployment does not install the storefront script, replay historical orders, or infer timestamps from undated landing/referring URLs. Install Archon's consent-aware capture script in a preview theme, grant the required consent, place a test order, and verify its dedicated note attribute reaches OMS and appears in Archon Orders & evidence with the original visit timestamp. Then repeat ordinary delivery to confirm the same retained evidence is deduplicated by Archon. Orders without that captured history remain unattributed. Any historical replay requires a separate, reviewed scope; this PR does not perform one.

Tests cover the actual outgoing payload with database/HTTP mocks, financial-field preservation, replay consistency, sanitized failure logging, absent evidence, duplicate attributes, invalid timestamps/URLs/IDs, and the 20-interaction limit. No new database writes or schema changes are introduced.
