# Procurement planning acceptance evidence

Inspected and implemented against base `6f033fe6` in `codex/procurement-planning-completion`, 2026-09-07. This ledger describes code and synthetic test evidence. It does not assert that a production setting, migration, scheduler, forecast, stock balance, vendor quote, or ETA is correct or activated.

## What the code definitely does

The existing planning authority is `generatePurchasingRecommendations` in `server/modules/procurement/purchasing-recommendation.engine.ts`. Both interactive analysis and durable daily recommendations consume it through `procurement.storage.ts:getReorderAnalysisData` / `getReorderAnalysis` and `purchase-recommendation-snapshot.service.ts:buildPurchaseRecommendationRunInput`. This work extends that authority; it does not add a second purchasing quantity calculation or vendor-send path.

## Inputs that are not proven

- **Usable warehouse stock:** `purchase-inventory-snapshot.query.ts:purchaseInventorySnapshotQuery` aggregates active variants and excludes only the explicit `quarantine` location type for both on-hand and reservations. This type is hard-ineligible in `inventory-availability-planner.ts:isPromiseEligibleLocation`. Nonpickable reserve remains counted, verified with real PostgreSQL. `returns.service.ts` receives and negative-adjusts damaged/defective returns in one inventory transaction, so those units already leave on-hand. A generic authoritative held-quantity ledger and other damage workflows remain unproven; no arbitrary hold/freeze or nonpickable subtraction was added.
- **Historical unit conversion:** the current stock and demand source queries multiply by current catalog `units_per_variant`. This inspection does not prove immutable historical conversion factors are used. No historical records or conversion logic were changed here.
- **ETA fidelity:** current expected-date inputs do not prove carrier possession, customs release, physical arrival or sale availability. Same-day planned receipts precede same-day demand in the diagnostic. Receiving and putaway remain the physical availability owners.
- **Demand correctness:** no production sales, promotions, recent stockouts, channel mix or seasonal data were reconciled to the user's spreadsheet. Synthetic correctness tests establish behavior, not forecast accuracy.
- **External reporting and tracking:** landed cost / production-transit valuation / Archon export and carrier integrations are outside this planning commit. Their separate evidence ledgers must establish actual downstream authority and runtime behavior.

## Failure behavior and rollout

Migration `223_purchase_planning_policy.sql` creates a procurement-owned singleton and append-only revision history, inserts a neutral revision 0, installs a revision immutability trigger and broadens forecast capture compatibility. Reapplying it is tested. It neither populates real product policies nor changes existing forecast observations.

Deploy migrations 223 and 225 before this application code. Migration 225 accepts the version-3 replacement capture and leaves all historical observations intact. Missing/uninitialized storage is a visible error; the owner does not silently substitute defaults for a broken or missing table. Invalid stored policy also fails visibly. The only neutral fallback in the pure parser supports legacy callers that provide no policy; it is not a failed-database fallback.

Rollback keeps the additive tables and history. If reverting behavior while this application remains deployed, save a neutral policy through the audited command. Older application code ignores the new table; existing version-1 observations stay readable, while version-2 growth and version-3 replacement observations require compatible readers. Do not delete history or relabel its cohort to make an older reader accept it.

The policy editor is within the existing planning settings dialog. Search returns at most 50 active catalog matches and says when the result is capped. Policy history displays the latest 50 immutable changes; the database retains every revision. Invalid quantities, duplicate products, impossible stages, missing product references, stale revisions and reused keys with changed payloads fail before committing a policy.

Writer topology adds exactly `procurement.purchase_planning_policy` and `procurement.purchase_planning_policy_revisions` to the procurement owner in `scripts/writer-ratchet/baseline.json`; no existing table gains another owner.

## Increment failure modes and assumptions

- Supplier thresholds compare the selected product subtotal in the supplier currency; tax, freight and discounts not yet quoted are not fabricated. If the selected bundle cannot be priced or is below its minimum, the existing PO transaction rejects with `SUPPLIER_BUNDLE_NOT_READY`. Free-freight thresholds are informational and never increase product quantities. RFQ authoring remains available for unresolved baskets.
- Replacement totals are spread across their inclusive calendar range using cumulative micro-piece allocation. This is an explicit daily distribution assumption, not evidence of an exact customer shipment date. Dated demand events model separate lumpy additions. Invalid dates, overlaps, unsupported precision and missing source references are rejected. Growth is not reapplied to explicit replacement quantities.
- Historical rate/cover displays retain the measured growth-adjusted daily rate; the stock target, dated order-by/arrival diagnostic and captured backtesting apply replacements. Forecast accuracy still requires real observed demand after the evaluation window matures.
- The bulk inventory reader still uses current catalog conversion factors and does not claim a proven generic held-stock ledger. Excluded quarantine quantity is retained in planning evidence and displayed separately.
- `purchase-planning-policy.runtime.ts:getPurchasePlanningPolicyService` constructs its PostgreSQL adapter lazily when planning is used. Importing unrelated procurement routes/storage no longer initializes that adapter; a failed actual planning read remains visible.
